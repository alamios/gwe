# Manual continuous control session

Implemented and prepared on 2026-10-02. This is an experimental session for the current host, not a
production/background service or Wayland acceptance. The installed Flatpak and personal database are
not replaced. Continuous fan control now uses an 85 C ceiling; reaching it stops manual control and
attempts automatic recovery. Brief trial mode retains its 60 C ceiling. Read-only current-host checks
reported driver 580.178.04 and a 94 C slowdown threshold; this does not validate elevated-load operation.

## Start and stop

Close installed GWE and other development windows first. From the repository, using the prepared
Python 3.12 interpreter and explicit read-only backup:

```bash
bash scripts/run_control_session.sh /path/to/prepared/python3.12 "$BACKUP_DB" build/session-service-v4
```

This one command checks inactive/failed service state, completes any outstanding recovery, resets the
expected failed state from fault tests and installs the reviewed bundle. An existing rollback copy is
retained under `/opt/gwe-fan-service.previous.<UTC timestamp>`; the updater creates another rollback
copy of the installation it replaces. Existing configuration is preserved. No packages are changed.

The wrapper temporarily stops CoolerControl and installs the bundle's root-owned runtime systemd
override. The override selects `run --continuous` and removes the 60-second lifetime; the watchdog,
process supervision and independent ExecStopPost recovery remain enabled. `KillMode=mixed` lets the
supervisor finish recovery before systemd kills remaining children on timeout; the session stop timeout
is 50 seconds. No boot enablement occurs.
The application opens with isolated settings, explicit backup access and no selected/applied curve.
Select a compatible curve and press **Apply selected curve**. **Restore automatic** releases it.
The updated source supports an opt-in named startup curve through the
[local installation preference](local-installation.md). It uses the same guarded acquisition once after
telemetry becomes available; faults and Restore never rearm it. The default remains explicit Apply.
Closing the application ends the session, stops/recovers the service, removes the runtime override
and restores CoolerControl's original active state only after recovery succeeds. Keep the launching
terminal open. Normal verified power changes remain committed on close, as documented in
[power control](power-control.md); this session does not install the special 250 W acceptance guard.
Power is available with a stable active curve when the installed service advertises the new capability.
Renewals continue during the separate power transaction; Restore remains available. Fan transitions
and recovery faults still block new power work. Older services keep Power disabled during active curves.

After the first successful update, subsequent sessions can reuse the installation without another update:

```bash
bash scripts/run_control_session.sh /path/to/prepared/python3.12 "$BACKUP_DB" --installed
```

## Recovery and limitations

The GUI renews the same five-second service lease once per second; continuous mode removes only the
ten-second GUI deadline. Lost/stale telemetry, a stale UI heartbeat, socket loss, explicit release and
application exit still initiate recovery. A service/worker failure cannot rely solely on GUI cleanup;
the existing watchdog and independent post-stop recovery remain in place. Startup never imports,
migrates or applies a saved profile. Faults never automatically reacquire a curve.

The root-owned `session.json` records the configured desktop UID, launcher PID/start time and original
CoolerControl state before cooling-service changes. The daemon validates that identity and watches a
Linux pidfd, preventing PID reuse from keeping an old session alive. Launcher exit, including SIGKILL,
ends the service and initiates independent post-stop recovery. This also covers closing a long session
after sudo authentication expires; wrapper cleanup uses noninteractive sudo and does not block for a
new password. Root recovery restores CoolerControl only after all GPU recovery succeeds, removes only
an override matching the installed template and retains the session record on failure. The override
grants write access only to its own runtime systemd directory for this cleanup under `ProtectSystem`.
Updates and uninstall refuse pending session records. Unknown overrides remain untouched.

Suspend/resume, extended real operation, driver/host failures and target-OS/Wayland remain unvalidated.
The thermal recovery boundary and graceful systemd/launcher cleanup still need hardware acceptance;
no additional load is generated by the launcher.

## Observed first continuous session and consolidated follow-up

The real client log shows active control from 01:36:32 to window close at 01:38:16 on 2026-10-02
(Europe/Madrid), about 104 seconds without a timed release. The service journal recorded RuntimeError
at shutdown; that message does not establish its cause. Independent read-only follow-up found automatic
fan policies, 250 W, no pending GPU/session record and CoolerControl active again. The first session
therefore provides extended-client evidence, not clean continuous-shutdown acceptance.

The follow-up addresses the trial-only thermal cap, possible termination of recovery children during a
whole-group SIGTERM, and cleanup after launcher loss or expired sudo authentication. The suspected
shutdown interaction is not a proven diagnosis of the observed RuntimeError. Simulated tests verify
normal 61–84 C curve updates and automatic recovery at 85 C, private session validation, PID reuse
rejection, real pidfd exit detection, CoolerControl restoration and retaining records on recovery failure.
The consolidated GTK check passes. Hardware verification of this complete revision remains pending.
The additional combined GTK check verifies a simulated 320 W power change without interrupting active
curve renewal, followed by explicit fan restoration. See the [CUDA load baseline and planned check](power-control.md).

### Launcher reset correction: 2026-10-02

The owner's update attempt stopped at `reset-failed` with a unit-not-loaded error. Independent inspection
found the regular unit file present, the service inactive with success, CoolerControl active, 250 W, both
fan policies automatic and no pending record. The failure happened before the wrapper's bundle update.
An inactive unit can be unloaded after recovery/reload; `reset-failed` is unnecessary in that state.
The launcher now rechecks ActiveState after recovery and resets only a failed unit. Eleven focused
launcher tests pass on both interpreters, including inactive/unloaded and failed-state cases. This is a
source-wrapper correction; the same reviewed bundle command can be rerun without rebuilding the bundle.

### Extended session accepted by the owner: 2026-10-02

Following the launcher correction, the real client logged active control from 11:45:17 to closure at
14:18:31 (Europe/Madrid), approximately 2 hours 33 minutes. It recorded one `power_verified` event
during that active session, without failure events in the session. The owner reported that use worked
well and reopened the old application afterward.

Independent read-only follow-up found the experimental service inactive with success, CoolerControl
active and no GPU or session pending record. The old application was already reopened: fan policies
were manual, power limit 320 W, temperature 63 C and GPU utilization 94%. These fan readings cannot
independently establish automatic policy between development shutdown and the old application's
startup. This accepts the observed extended session and clean service/session-record shutdown,
not suspend/resume, forced launcher death on hardware or a recorded temperature peak.

Power retention on close behaved as designed: returning to the old application did not restore 250 W.
No GPU settings were changed during follow-up. A separate [local desktop installation](local-installation.md)
now provides snapshots, retained rollback and controller checks before privileged session preparation.
The owner explicitly chose to retain 320 W while continuing CUDA work. Installation does not start a
session or interrupt that workload; target-OS migration and remaining recovery acceptance stay pending.
